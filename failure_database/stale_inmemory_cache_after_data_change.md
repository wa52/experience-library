# 内存缓存"已加载即跳过"导致数据变更后索引不刷新（BM25）

## 问题现象
Web 服务运行中通过界面/定时任务新增文档后，`/api/v1/status` 里 `vector_count` 增加了，
但 `bm25_chunks` 仍是旧值；混合检索的 BM25 一路永远搜不到新内容，向量一路却正常。

## 影响项目
- langchain-kb（定时同步经验库功能）

## 原因
`rebuild_bm25()` 的优化逻辑：只要 `_bm25_retriever` 已加载进内存就**无条件跳过重建**
（"数据未变，避免重复解析 pickle"）。但它从没校验数据是否真的没变——
服务进程内发生索引/同步后集合数量变了，内存索引仍然是旧的，且没人失效它。
这是典型的**缓存失效缺失**：优化假设成立的前提（数据不变）没有被检查。

## 解决方案
跳过前先比对内存索引文档数与集合实际数量，不一致就强制全量重建：

```python
if _bm25_retriever is not None:
    in_mem = _bm25_doc_count(_bm25_retriever)
    if expected_count is not None and in_mem == expected_count:
        # 数据未变才跳过
        return
    _bm25_retriever = None   # 数据变了，强制重建（落到磁盘缓存校验/全量重建）
```

## 教训
- 任何"已加载就跳过"的缓存优化，**必须校验缓存有效性的依据**（如版本号、计数、mtime、hash），否则数据变更后静默失效。
- 长驻进程（Web 服务）里做数据写入后，要确认所有相关内存缓存都被正确刷新，不能只测 CLI 一次性流程（CLI 每次新进程，天然没有"已加载"的坑，掩盖了问题）。
