## Stage 1: Requirement Analysis

**目标：** 理解当前知识库状态，明确整理目标和范围。

**核心活动：**
1. 扫描知识库根目录，记录当前目录结构
2. 识别重复、过期、无归属的文件
3. 明确本次 Workflow 的执行范围（全库 / 子目录 / 特定主题）
4. 输出需求分析报告

**出口条件：**
- 需求报告已写入 `reports/requirement/`
- 执行范围已明确
- 风险项已列出

---

## Stage 2: Architecture Design

**目标：** 设计知识库的目标目录结构和元数据规范。

**核心活动：**
1. 设计分层目录结构
2. 定义 Metadata 字段规范
3. 定义 Tag 分类体系
4. 设计索引策略
5. 输出架构设计报告

**出口条件：**
- 架构报告已写入 `reports/architecture/`
- 目标目录结构已确定
- Metadata 规范已定稿

---

## Stage 3: Migration Planning

**目标：** 将架构设计拆解为可执行的任务列表。

**核心活动：**
1. 将目录迁移拆分为具体任务
2. 确定文件移动顺序（先结构、后内容）
3. 评估每个任务的风险和依赖
4. 输出执行计划

**出口条件：**
- 执行计划已写入 `reports/planner/`
- 每个任务有明确的验收标准
- 任务无遗漏

---

## Stage 4: Knowledge Migration

**目标：** 按计划执行文件移动、重命名、元数据写入。

**核心活动：**
1. 创建目标目录结构
2. 按任务列表逐项移动文件
3. 写入 Metadata
4. 记录执行日志
5. 必要时回滚

**出口条件：**
- 执行日志已写入 `reports/execution/`
- 文件已移动到目标位置
- Metadata 已写入
- 索引已更新

---

## Stage 5: Review

**目标：** 审查迁移结果，确保结构正确、内容完整。

**核心活动：**
1. 检查目录结构是否符合架构设计
2. 检查文件是否完整迁移
3. 检查 Metadata 是否正确
4. 检查是否有残留文件
5. 输出审查报告

**出口条件：**
- 审查报告已写入 `reports/review/`
- 问题列表已记录
- 严重问题退回 Stage 4

---

## Stage 6: Validation

**目标：** 验证知识库的功能完整性和数据一致性。

**核心活动：**
1. 验证索引可正常生成
2. 验证所有链接有效
3. 验证 Metadata 可解析
4. 验证无重复文件
5. 输出验证报告

**出口条件：**
- 验证报告已写入 `reports/validation/`
- 所有检查项通过
- 不通过项退回对应阶段

---

## Stage 7: Evaluation

**目标：** 对本次 Workflow 执行结果进行综合评分。

**核心活动：**
1. 按 `workflow_score.md` 逐项评分
2. 对比执行前后知识库状态
3. 总结本次经验教训
4. 输出最终评分报告

**出口条件：**
- 最终报告已写入 `reports/final/`
- 评分已记录
- 经验教训已归档

---

## 退回路径

| 当前阶段 | 可退回阶段 | 退回条件 |
|----------|-----------|----------|
| Architecture | Requirement | 需求不清或范围不合理 |
| Planner | Architecture / Requirement | 架构不可执行或需求遗漏 |
| Migration | Planner / Architecture | 任务缺失或架构不合理 |
| Review | Migration | 迁移错误或遗漏 |
| Validation | Review / Migration | 验证不通过 |
| Evaluation | 任意阶段 | 评分不达标 |

---

## 执行模式

| 模式 | 适用场景 | 说明 |
|------|---------|------|
| 全量 | 首次整理或大规模重构 | 从 Stage 1 到 Stage 7 完整执行 |
| 增量 | 日常新增知识入库 | 从 Stage 4 开始，跳过需求/架构/计划 |
| 修复 | 发现单点问题 | 从 Review 开始，仅验证修复项 |
